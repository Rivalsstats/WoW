# Blizzard Pre-Season Period Quirk

Blizzard's mythic-keystone season details API includes the period that *ends exactly at the season start* (for example season 17's period 1055 in all regions). It has zero runs. Left in place, tables and queries that derive week numbers from `season_periods` count a phantom "week 1" while ordinal-position-based views (`aggregated_key_throughput`, the "Key Throughput" chart) do not, so the week axes disagree by one (the dashboard's "Keys per Week" would start at Week 2 against Week 1 on keys/min).

`backend_scripts/fetchSeasonAndPeriodInfo.py` skips periods where `end_timestamp <= season_start`, applied both to `periods.json` and to the `season_periods` insert via `databaseConnector.insert_season_periods`. Patch annotations index into the filtered `periods.json`, so all three week axes agree.

`insert_season_periods` is `INSERT IGNORE`, so the filter is only prophylactic: a phantom row inserted before the filter existed (or by an out-of-band writer) lingers in `season_periods` and re-running the fetch never removes it. When a live season's "Keys per Week" still starts at Week 2 even though `periods.json` is clean, the stale phantom row is the cause; delete it directly, e.g. `DELETE FROM season_periods WHERE season = <id> AND end_timestamp <= <season_start_ms>;`.

Two defenses live in `generateDashboardPage.createKeysPerWeek` so the chart survives a polluted table without any DB write:
- It normalises week numbers so the earliest week present renders as "Week 1" (`offset = min(week) - 1`). A leaked phantom is always the zero-run first week, which the keys-per-week SQL already drops, so its only effect is a uniform +1 that the offset cancels. Real gaps between weeks are preserved (never compressed), unlike the ordinal `Key Throughput` axis. Labels are `f"Week {n}"` to match that chart's format exactly.
- With only one week of data (season week 1) a single weekly point looks sparse, so it switches to a per-day breakdown: `FETCH_RUNS_PER_PERIOD` groups by `(week, day_in_week)` and `createKeysPerWeek` renders `Day 1..Day N` when exactly one week is present, collapsing back to weekly totals once a second week exists. In day mode the card title, x-axis, and mobile heading follow the `period_grain` template flag, and patch annotations (week-index based) are suppressed.

The "Key Throughput" (keys/minute) chart follows the same week-1 grain. `aggregated_key_throughput` is per (season, region, period) with only `run_count + max_ts` and must NOT gain a per-day grain. In week 1 `_daily_throughput_series` redraws only the chart labels + series as per-region daily lines from raw per-(region, day) run counts (`fetch_runs_per_region_day`, a runs-table aggregate with no schema change); `compute_key_throughput(..., daily_region_rows=...)` gets those rows only when the season is in its single-week grain. Each region's day rate = region_day_count / day-minutes with day boundaries anchored at THAT region's own period start (numerator and denominator share one region-relative clock); completed day = 1440 min, the region's last/ongoing day = elapsed (that region's `max_ts` - the day start); the Overall line sums the available per-region rates per day. Colours/order reuse `REGION_COLORS` / `_region_sort_key` / `OVERALL_COLOR`. Fails loudly if a region's static bounds are missing. 2+ weeks keeps the untouched per-region weekly view from `aggregated_key_throughput`, byte-for-byte. `period_grain` is decided once from `runs_per_period` and shared by both cards.

Headline-stays-weekly rule: the KPI card literally reads "/min this week", so `current_total` / `season_total` / `delta_pct` are ALWAYS the weekly figures (`combined_rate` of the latest period + season overall-average from the `aggregated_key_throughput` rows), even in day grain. Only the chart grain changes. Do NOT recompute the headline from the daily series (e.g. `data[-1]`), or the number jumps to the last, partly-elapsed day's spike instead of the week-so-far combined rate.

Daily-region-set rule: the daily chart's region set MUST come from the aggregated `rows` (the canonical set the weekly chart uses), NOT from the runs query. `aggregated_key_throughput` is a persisted snapshot; the live `fetch_runs_per_region_day` query can legitimately return a smaller region set than that snapshot (runs retention, or `season_periods` bounds that changed after the snapshot was built), so sourcing regions from the runs query silently drops regions (e.g. KR/TW) from ONLY the daily chart while the weekly chart still shows them. `fetch_runs_per_region_day` therefore returns `period_id` (not a COUNT-derived week number), and `_daily_throughput_series` iterates regions from `rows`, pins each to the exact `period_id` it carries there, and pulls that region+period's day counts (a canonical region with no matching day rows draws an all-None empty line, keeping the legend in step). A region absent from BOTH `rows` and the runs query (season not launched in that region yet) is correctly omitted from both charts — that is expected, not a bug.

If week numbering ever looks off by one at a new season, check this quirk first.
